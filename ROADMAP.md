# SolidSecurity Mission-Driven Roadmap R2

## Canonical status

Mission R2 and M1 are canonical. The predecessor convergence step is complete. Active product work begins with **R2-01 / R2-WP01 — Executable assurance kernel** and remains governed by central Control Autonomy V3.1.

The roadmap retires the highest-value uncertainty with the smallest coherent safe change.

Core rules:

- customer reality over internal completion;
- managed service before self-service;
- evidence and qualified professional review before assurance claims;
- required evidence class must match the claim;
- executable/falsifiable model before broad UI/platform work;
- controlled real-world learning before broad productization;
- simplest safe architecture first;
- one common-control backbone rather than framework silos;
- deterministic validation where mechanical, independent B1 where consequence warrants it;
- mission evidence, not issue closure, determines progress.

## Preserved foundations

R2 preserves:

- Requirement / Control / ClientImplementation / Evidence / Assessment / ProfessionalReview / Decision separation;
- Proof Ladder and AI Authority Matrix;
- common-control and evidence reuse;
- managed-service proposition;
- Operator Workspace / Client Dashboard / Interaction Layer product model;
- shared PostgreSQL + private object-store direction;
- runtime/tenant/evidence safety requirements;
- no `scanner pass -> compliance PASS` shortcut;
- no autonomous final legal/compliance/certification/risk-acceptance authority.

**Mission focus:** SS-SC-04, SS-SC-06

Protected standard text remains reference-only unless redistribution rights are established.

## R2-02 — Launch, economics, IP and professional-trust readiness

**Workpackages:** `R2-WP02` issue #33 + `R2-WP03` issue #34  
**Evidence target:** E0 plus E3 where available

### A. Care launch and GTM

Define/test one primary Care ICP, disqualifiers, applicability-correct positioning, competitor/alternative landscape, incumbent-MSP response, first-10 acquisition hypothesis and channel hypotheses. Supplier remains secondary until market evidence promotes it.

### B. Bottom-up unit-economics

Build the **bottom-up unit-economics** model from workflow step, professional/reviewer minutes, loaded rate, cadence, customer minutes, AI accept/edit/reject, evidence/assertion reuse and onboarding payback.

Prices remain hypotheses until real evidence supports them.

### C. Repository/IP boundary

Public repository contains deliberately public-safe product/model/schema/synthetic material. Proprietary detailed mappings, evidence-sufficiency logic, private prompts, detailed GTM/economics, accumulated operating intelligence, client data and secrets are restricted/private by default.

Do not create private infrastructure speculatively; create a separate private storage/repo only when the first restricted artifact actually needs durable storage.

### D. Professional trust and liability

Before customer-facing `VERIFIED`, every applicable competence, authority, independence, capacity, escalation, liability/insurance, contract/report-language and DPA/subprocessor prerequisite must be satisfied and appropriately reviewed.

`project B1 != customer professional review != external independent assurance/certification`.

## R2-03 — Bounded real design partner

**Workpackage:** `R2-WP04` / issue #35  
**Evidence target:** E2 + E3

Goal: contact reality before broad productization.

Entry requires all of:

- R2-WP01, R2-WP02 and R2-WP03 readiness;
- minimum safe shared tenant-aware data plane;
- tenant-isolation negative proof;
- private evidence-store boundary;
- immutable evidence version/hash integrity;
- encrypted off-site backup plus actual restore proof;
- applicable security/data/contract/professional gates;
- explicit principal real-client-data authorization.

A **bounded real design partner** does not require the complete future Operator Workspace or Client Dashboard. Use the smallest safe tooling that preserves authoritative dossier, provenance and authority boundaries.

Measure actual evidence availability, ambiguities, response latency, review burden, workflow effort, AI acceptance/edit/rejection, customer comprehension/value, competitor/alternative response, channel/first-10 outcomes, incumbent-MSP objections, loss reasons and willingness-to-pay.

Commercial validation requires at least one bounded pricing/package hypothesis supported by observed willingness-to-pay or commercial commitment. Rejected/inconclusive pricing stays open for retest.

## R2-04 — Productize from observed friction

**Workpackage:** `R2-WP05` / issue #36  
**Evidence target:** E2/E3 progressing to E4

Priority order:

1. authoritative dossier/runtime primitives actually required by real delivery;
2. Operator Workspace functions that remove repeated professional work;
3. Interaction Layer functions that remove repeated customer friction;
4. Client Dashboard around proven visibility needs;
5. automation ranked by measured operator/customer/reviewer minutes and assurance impact.

Minimum runtime remains:

`shared PostgreSQL + tenant_id + server-side authorization/RLS + private object store + immutable evidence versions/hashes + audit events + tested backup/restore`.

Client visibility must explain current state, demonstrably arranged controls, attention points, actions/decisions and reports without requiring GRC/control-ID literacy and without a misleading single compliance percentage.

## Capacity rule

The roadmap is a priority system, not a commitment to build every option. Central Control V3.1 determines eligible work; semantic implementation capacity is intentionally one A1 lane and semantic assurance one B1 lane.

## Repository visibility rule

Anything public is treated as permanently disclosed. Public-safe methodology may be deliberately published; client data, secrets and proprietary/restricted operating intelligence remain outside this repository unless an explicit release decision says otherwise.
