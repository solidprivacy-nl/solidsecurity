# Backup and Recovery V1

Status: `DESIGN / NO CUSTOMER SLA CLAIM`

## Principle

A backup is not evidence of recoverability. SolidSecurity treats backup creation, backup integrity and successful restoration as three separate controls.

## Failure domains

The design protects against at least:

1. accidental record/object deletion;
2. application defect or bad migration;
3. credential compromise or malicious deletion;
4. primary database/storage service failure;
5. primary provider/account-level failure;
6. corruption or incomplete backup;
7. operator error during restoration.

No single mechanism covers every failure domain.

## Structured-state backup

### Primary protection

Use the managed database backup capability of the selected Postgres provider. Under the current Supabase candidate, paid projects receive managed daily database backups; PITR is an optional higher-cost recovery mechanism.

### Independent copy

Create an encrypted logical export on a separate schedule and copy it to the secondary recovery provider.

Requirements:

- generated by a dedicated backup identity;
- encrypted before independent-provider storage;
- contains schema/migration version metadata;
- produces checksum and manifest;
- backup completion is recorded in `backup_run` state;
- failed/late backups alert operations;
- restore procedure does not depend on the original primary project still existing.

The first production profile should default to cost-conscious daily independent export unless the contracted RPO requires a shorter interval.

## Evidence-object backup

Supabase database backups do not contain the underlying Storage objects. Evidence recovery therefore has its own pipeline.

For every evidence version eligible for persistence:

1. validate upload and classification;
2. compute content hash;
3. write immutable primary object;
4. record authoritative metadata;
5. copy/replicate the exact version to the independent recovery store;
6. verify secondary object size/hash or recovery-package manifest;
7. mark `SECONDARY_VERIFIED` only after verification.

The secondary copy uses the same opaque evidence/version identity and must not silently overwrite an existing version.

## Secondary recovery provider

Cloudflare R2 is the current candidate because it is a separate provider/failure domain from Supabase, encrypts objects at rest, supports S3-compatible access, high durability, lifecycle rules and bucket locks.

Use private buckets only. Backup credentials are write/read scoped to the smallest feasible recovery namespace and are separate from normal application object credentials.

Bucket locks may protect recent backup/audit prefixes from deletion or overwrite for a configured recovery window. Lock duration must align with the documented retention/deletion policy; indefinite lock is not a default.

Older backup material may move to an infrequent-access class when operationally and economically justified.

## Backup manifest

Each backup batch produces a manifest containing at minimum:

- backup/run id;
- tenant/runtime id;
- source environment/schema version;
- creation start/end time;
- included logical database artifact identity and checksum;
- included evidence version ids and checksums or manifest root;
- encryption profile/key reference;
- target recovery location;
- retention/expiry state;
- verification result;
- software/version that created the backup.

A manifest contains identifiers/hashes, not plaintext evidence content.

## Restore testing

### Automated frequent test

At least on a scheduled basis, retrieve a sample of secondary evidence objects, decrypt where applicable and compare the resulting hash with the authoritative evidence-version hash.

### Synthetic database restore

Restore the latest independent logical database backup into an isolated synthetic recovery environment and verify:

- migrations/schema can load;
- expected tenant/dossier counts are present;
- critical relationships and foreign-key invariants hold;
- no production credentials are restored as usable secrets.

### Full dossier reconstruction

Periodically execute a synthetic end-to-end recovery:

`database backup + evidence recovery store + control-plane release -> reconstructed client dossier`

Acceptance requires the reconstructed evidence hashes and review references to match the expected state.

No recovery drill uses real client data in development/test environments. A production restore exercise requires a separately approved isolated recovery environment.

## Recovery objectives

Engineering profiles are defined in `DATA_RESILIENCE_ARCHITECTURE.md`. Actual RPO/RTO are measured from restore tests and may not be marketed or contracted until proven.

Every restore test records:

- recovery point achieved;
- recovery time achieved;
- missing/corrupt objects;
- manual steps required;
- failures/limitations;
- corrective actions.

## Retention and deletion

Backup retention is configuration/contract driven. The recovery system must support different policies without embedding client-specific durations in code.

When active client data is deleted:

- primary records/objects follow the approved purge process;
- backup copies enter their documented expiry path;
- legal/contractual hold is explicit and auditable;
- the client is not told data is fully purged while protected backup copies remain recoverable;
- after final expiry, recovery copies and associated recoverable encryption material are removed according to the approved process.

## Database PITR decision

PITR is a service-level decision, not an architectural default. Current Supabase pricing makes PITR materially more expensive than daily backups for early low-volume projects. Enable it when a customer's required RPO/business continuity justifies the cost and after the restore process is tested.

## Monitoring

Minimum operational indicators:

- last successful primary DB backup;
- last successful independent DB backup;
- percentage of persistent evidence versions with `SECONDARY_VERIFIED`;
- oldest unprotected evidence version;
- backup verification failures;
- last successful object restore test;
- last successful database restore test;
- last successful full dossier reconstruction;
- upcoming backup-retention expiry/hold exceptions.

## Prohibited shortcuts

- calling provider replication a complete backup strategy;
- relying only on a database backup for object storage;
- retaining only one provider/account copy;
- keeping backups forever because deletion is difficult;
- overwriting old evidence objects;
- restoring production backups into ordinary developer environments;
- declaring an RPO/RTO from configuration without measuring recovery.
